## 0. Problem statement

BYOC F0–F4 is complete and Architect-APPROVED, but every mesh piece was built **additively, behind the seam** — built and unit-tested, never wired into the live dispatch loop. The live desktop still runs the **bake-off**: `crates/apohara-desktop-dioxus/src/coroutines/dispatch_loop.rs::run_dispatch` (~L66–333) dispatches **every** available provider against the **same full objective**, then `winning_diff()` (L658) picks the best — N agents redo the same work. The vision (R1) is the opposite: a **DAG decomposed into disjoint slices**, distributed so **no blade is idle**, blades **coordinating live** over the mesh, an integrator consolidating **incrementally**. The `Coordinator` exists (`crates/apohara-coordinator/src/coordinator.rs`) but the desktop has **no dependency on it** (confirmed: `crates/apohara-desktop-dioxus/Cargo.toml` lists dispatch/token/episodic/mcp/hooks-server — not coordinator, not safety). All 13 `.tick()` callers are tests.

The transition rewrites `run_dispatch` from "fan-out-same-objective + pick-winner" to "plan → distribute-disjoint → coordinate → integrate." This is the load-bearing risk: **the bake-off works today and ships.** We must not regress it until the mesh is proven green.

## 1. RALPLAN-DR Header

### 1.1 Principles (load-bearing, 5)

1. **Additive until proven.** The mesh path lands behind a NEW flag (`APOHARA_MESH`), default OFF. The bake-off remains the default `run_dispatch` body until the dogfooding criterion passes green. Discipline inherited verbatim from F0–F4: "do NOT regress the working bake-off until mesh is green."
2. **Integrate, never reinvent.** Every primitive (coordinator, `assign`, planner, consensus, mailbox peek/ack, phase permissions, audit `mesh()`, utilization) is built and unit-tested. Stories WIRE them; they do not re-author logic. A story that rewrites an existing pure function is a smell.
3. **One-way dependency edges.** `apohara-dispatch → apohara-coordinator` (never back — the `SchedulerStore` trait lives in coordinator, the impl in dispatch). `apohara-hooks → apohara-hooks-server` (never back). The desktop may depend on all of them. Any new edge that would cycle is rejected at design, not discovered at `cargo build`.
4. **Single-writer invariants stay sacred.** `runSerialized` per binary (the 120s-hang past-incident), `INTEGRATOR_LOCK` single HEAD writer (`lifecycle::merge`), the cross-process advisory claim lock, atomic file writes (§0.8). The mesh path reuses these exact guards; it never opens a second concurrency model. **Claims must never leak**: every claim is released or reaped — the on-demand drive loop reaps-on-exit, and the `utilization_watcher` reaps stale dead-PID claims between runs (Architect-required; see D4). A `Claimed` record with a dead PID that nothing reaps is a liveness bug, not an acceptable v1 gap.
5. **Human stays in the loop.** The swarm *proposes*; Pablo *decides* (anti-`apohara auto`). Review/merge is human-gated; PLAN phase is read-only; the existing `PermissionRequest` overlay is the enforcement point.

### 1.2 Decision Drivers (top 3)

- **D-Driver-1 — Zero regression of a shipping feature.** The bake-off is live and demoed. Coexistence + flag-gating + a kill-switch back to bake-off is non-negotiable. Weight: highest.
- **D-Driver-2 — Make the F0–F4 investment real.** ~10 stories of mesh primitives are inert. The transition's *whole value* is wiring them into one live loop. A plan that wires only 50% leaves the mesh theoretical (pre-mortem Escenario from F2.0).
- **D-Driver-3 — Iteration-sized, independently-verifiable stories.** DELIBERATE mode + concurrency/HEAD/auth-critical seams demand each story be atomically committable, gated (build + test + clippy `--all-targets -D warnings`), and adversarially reviewed where it touches the claim/HEAD/auth path.

#### D1 — Replace the bake-off entirely, or coexist behind a flag?

| Option | Pros | Cons |
|---|---|---|
| **D1-A — Coexist behind `APOHARA_MESH` (default OFF), bake-off default ON** ✅ CHOSEN | Zero regression risk (D-Driver-1); instant kill-switch back to a known-good path; lets the dogfooding test compare mesh vs bake-off on the SAME repo; aligns with the F0–F4 `APOHARA_RUST_DISPATCH`-gating discipline already in the codebase. | Two dispatch bodies to maintain transiently; a `match flag` fork at the top of `run_dispatch`; risk the bake-off branch bit-rots (mitigated: keep its tests). |

The bake-off body and its 14 unit tests in `dispatch_loop.rs` stay intact.

## 2. Pre-mortem (DELIBERATE — 4 failure scenarios; #4 added in the Architect revision)

### Escenario 1 — "The mesh regressed the demo." (probability: medium · impact: critical)
**Failure:** The mesh body has a bug (deadlock on `INTEGRATOR_LOCK`, a claim never released, a DAG that never drains). Because it shares `run_dispatch`, the shipping demo now hangs or produces no diff.
**Why plausible:** The mesh loop is new control flow over the same single-writer locks; a `while not-drained` that mis-computes "drained" loops forever; a panic in the tick path strands the run.
**Mitigations:**
- **M1.1 (Principle 1):** `APOHARA_MESH` defaults OFF. The demo path is literally untouched bytes. A regression in the mesh body cannot affect a session that didn't opt in.
- **M1.2:** Hard iteration cap on the on-demand loop — `MAX_TICKS` (provisional default **600**, tunable via `APOHARA_MESH_MAX_TICKS`). Rationale: the drive loop polls at ≈1s/tick and the coordinator's reaper TTL default is **5 min** (`coordinator.rs` `ttl_ms = 5 * 60 * 1000`); 600 ticks ≈ 10 min ≥ 2× the stall window, so the bound only trips well after the reaper has had a full chance to release a dead slot (the reaper, not the bound, is the normal exit). If the DAG hasn't drained after `MAX_TICKS`, the loop exits, surfaces what integrated, and flips status to Idle (never an infinite hang). Mirrors the bake-off's bounded `for p in providers`.
- **M1.3:** Every store call in the mesh body is best-effort-logged exactly like the bake-off (`tracing::warn!` + continue), never `unwrap()` on a runtime path — a single blade/claim/merge failure degrades to "that slice failed," not a dead loop.
- **M1.4 (verification):** The dogfooding e2e (story #7) runs the mesh path on a clone of THIS repo and asserts a real green integrated diff before the flag is ever recommended for default.

### Escenario 2 — "Two blades clobbered HEAD / a claim leaked." (probability: medium · impact: high)
**Failure:** The new per-assignment claim races the reaper; or two `assign` placements on the same binary slip past the serialization budget; or the integrator merges two slices that touched the same file and silently loses one; or **a blade dies between runs and its `Claimed` dead-PID record is never reaped** (Architect's liveness gap).
**Why plausible:** The claim key changed (node id vs `{provider}-{seq}`); `assign`'s `in_flight` seed could be stale if read before a just-landed claim; `INTEGRATOR_LOCK` is correct only if every merge goes through `lifecycle::merge`; the on-demand loop alone only reaps while a run is active.
**Mitigations:**
- **M2.1:** Seed `assign`'s `current_in_flight` from `ClaimStore::list` IMMEDIATELY before each tick's placement (not cached), so a claim that landed last iteration is counted. The claim store's advisory lock is the source of truth, not the in-memory ledger.
- **M2.2:** All merges route through `lifecycle::merge` (the `INTEGRATOR_LOCK` single HEAD writer) — the mesh body reuses the bake-off's exact `commit_worktree` → `lifecycle::merge` → `MergeResult::{Success,Conflict}` block (`dispatch_loop.rs:274–299`), including `preserve_on_fail` on conflict. No new merge path.
- **M2.3:** The planner produces **file-disjoint** slices (`planner.rs` fan-out: one `impl-<area>` per path token), so conflicting slices are structurally rare; a conflict that still occurs is handled (branch preserved, node Failed), never silently dropped.
- **M2.4 — reaper liveness (Change 1, pulled OUT of deferrable #6):** (a) the on-demand loop reaps-on-exit (exits only after a final reaping tick leaves no `Claimed|Running`); (b) the `utilization_watcher` reaps stale dead-PID claims between runs. A leaked claim is now structurally impossible to strand — it is released by one of the two PID-liveness-gated reapers. The reaper never touches a *live* PID.
- **M2.5 (verification):** Adversarial code-review (concurrency/HEAD/auth) on stories #1, #2 (the reap call), and #6. Integration test: two disjoint slices both integrate to a clean mesh diff; a deliberately-conflicting pair yields one Success + one preserved-branch Failed, HEAD never corrupted; a dead-PID claim is reaped on-exit (Story #1) and by the watcher with no run active (Story #2).

### Escenario 3 — "The DAG was garbage, so the swarm did nothing useful." (probability: medium · impact: medium)
**Failure:** `derive_areas` can't split the objective → a 3-node linear `plan→implement→verify` DAG → effectively one implement slice → no parallelism, mesh ≈ a slow single agent, dogfooding shows no win over bake-off.
**Why plausible:** Real objectives are prose, not `src/a.rs and src/b.rs`. The heuristic is deliberately simple (zero-token).
**Mitigations:**
- **M3.1:** The linear fallback still produces a valid, claimable, integrable DAG (≥2 nodes, real deps) — correctness is preserved even when parallelism isn't. The mesh never *breaks* on a thin DAG; it just doesn't *win*.
- **M3.2:** `plan_master(objective, areas)` accepts explicit `areas` — a future planner UI / consensus refiners enrich decomposition without touching the loop. The seam is open.
- **M3.3:** Consensus mode (`APOHARA_CONSENSUS=1`, ≥2 refiners) lets blades add slices to a thin draft (`consensus_refine` appends new nodes / unions deps) — the documented path to better decomposition for critical objectives (R9).
- **M3.4 (observability):** The utilization dashboard's `zero_idle_ok` + `ready_count` (now fed real numbers) makes a thin DAG *visible*: low `ready_count`, blades idle → the operator sees the swarm is under-utilized and can refine the objective.

### Escenario 4 — "The 2nd run did nothing — the DAG was already `done`." (probability: HIGH if unfixed · impact: high) — Architect-surfaced
**Failure:** Pablo runs a mesh objective, it completes; he runs a 2nd objective on the SAME repo and the swarm dispatches NOTHING — a silent empty-diff no-op, no error, no work.
**Why plausible:** `plan_master` node ids are plan-local (`plan`/`integrate`/`impl-*`) and `TaskGraph::add_node` REPLACES on duplicate id while the persisted `done` set ACCUMULATES on disk. The 2nd `build_master_plan` re-creates the same node ids over a store that already records them `done` → `ready_tasks` is empty → the drive loop exits immediately with no diff. This is the single most likely "it silently did nothing" report.
**Mitigations:**
- **M4.1 (Change 2 — primary):** Per-run DAG namespace — `TaskGraph::new(<repo>/.apohara/tasks/<run-id>)` (and the matching per-run claim/scheduler root). Every run starts from a clean, fully-claimable DAG; the prior run's `done` set lives in a different subdir and cannot poison the new run.
- **M4.2:** This *also* dissolves OQ3 (capacity>1 / retry id-collision): a retried node under a fresh run-id can't collide with the previous attempt's record.
- **M4.3 (verification):** Story #1 acceptance criterion — "a 2nd mesh Run on the same repo produces a fresh, fully-claimable DAG (no `done`-poisoning)"; integration test runs twice on one TempDir repo and asserts the 2nd run dispatches `plan`.
- **M4.4 (observability):** Were it ever to regress, the utilization dashboard's `ready_count = 0` immediately on a fresh objective is the tell — the operator sees zero ready work where there should be a `plan` node.

## 3. Story Decomposition

> Ordered. Each story: atomic commit on `feat/apohara-catalyst`, flag-gated, gate = `cargo build --workspace` + targeted `cargo test` + `cargo clippy --workspace --all-targets -D warnings`. Stories touching claim/HEAD/auth get an adversarial code-review pass. Story #1 is the core Coordinator→`dispatch_loop` wiring; everything after is a fold-in or a lift.

### Story #1 ⭐ — Core mesh dispatch body: Coordinator + assign + planner wired into `run_dispatch` (flag-gated)
**Goal:** A new mesh branch in `run_dispatch` that plans a DAG, then drives it to completion via `Coordinator::tick` + `assign`, reusing the bake-off's spawn/gate/integrate primitives. Default OFF.
**Files:** `crates/apohara-desktop-dioxus/src/coroutines/dispatch_loop.rs` (new `run_dispatch_mesh` body + a top-of-`run_dispatch` fork).
**New Cargo edge (Change 5):** `crates/apohara-desktop-dioxus/Cargo.toml` += `apohara-coordinator = { path = "../apohara-coordinator" }`. Acyclic (Architect-confirmed): desktop → coordinator, coordinator never → desktop; the `SchedulerStore` trait is in coordinator, `DispatchSchedulerStore` impl in `apohara-dispatch` (already a desktop dep).
**Approach (integrate, do not reinvent):**
1. Add `mesh_enabled(env: Option<&str>) -> bool` (opt-in: `== Some("1")`), pure + unit-tested, beside the `is_enabled` usage.
2. `run_dispatch` forks: `if mesh_enabled(APOHARA_MESH) && is_enabled(APOHARA_RUST_DISPATCH) { run_dispatch_mesh(objective).await } else { <existing bake-off body unchanged> }`.
3. **Per-run DAG namespace (Change 2 — load-bearing).** `plan_master` ids are plan-local (`plan`/`integrate`/`impl-*`) and `TaskGraph::add_node` REPLACES on duplicate id while `done` accumulates — so a naive 2nd mesh Run on the same repo would see a pre-`done` DAG and dispatch NOTHING (silent empty-diff no-op). Fix: scope each run's **TaskGraph (and its `done` set)** to its own subdir. Primary: `TaskGraph::new(repo/.apohara/tasks/<run-id>)` where `run-id = run-<unix_ts>-<short-rand>`. **Claims stay at the shared root** `repo/.apohara/claims` — only the TaskGraph/done set must be per-run to fix the poisoning; the claim store is already keyed by node id and reaped by PID-liveness, so a single shared `ClaimStore` is correct and lets the `utilization_watcher`/`claim_watcher` (which read one claims root) keep seeing every run's claims. (Path b fallback: `check_with_phase` unit-level deny in `apohara-safety`, no live caller.)
- **Reaper unification (reuse):** `coordinator_reaps_stale_claim_over_real_storage` (`scheduler_store.rs:135`) — assert it runs inside the mesh drive loop (reap-on-exit) too.

## 5. ADR — Bake-off → Collaborative-Mesh Transition

**Decision.** Land the collaborative mesh as an **additive, runtime-flag-gated** (`APOHARA_MESH`, default OFF) alternative body inside `dispatch_loop.rs::run_dispatch`, wiring the already-built F0–F4 primitives (`Coordinator` + `SchedulerStore`/`DispatchSchedulerStore`, `distribution::assign`, `planner::build_master_plan`, opt-in `consensus_refine`, mailbox peek/ack push, `decide_phase`, audit `mesh()`, utilization) into one **on-demand drive loop** (D4-B) that plans a **per-run-namespaced** file-disjoint DAG, distributes slices with no-same-binary-parallelism + anti-idle, coordinates blades over the existing mesh (single blade/claim/pane_key/recipient identity, scoped per run), reaps claims on-exit + via the `utilization_watcher` between runs, enforces PLAN-phase read-only on the **live F2.0c CLI claim-guard exit-2 path** (`guard_decision`/`check_claim` in `crates/apohara/src/main.rs` — the only PreToolUse block Claude Code honors; the hooks-server response is discarded by the installed hook), and integrates incrementally through the existing `INTEGRATOR_LOCK`. The mesh stories feed the SAME `DagTask`/`TASKS` signal + `ClaimStore` records the existing redesign already renders (see §6), so the redesigned Board/Graph/Active-Providers surfaces light up without UI rework. The bake-off remains the default, untouched path until the dogfooding e2e proves the mesh green.

**Drivers.** (1) Zero regression of a shipping feature (the bake-off works). (2) Make the inert F0–F4 investment real. (3) DELIBERATE-mode demands iteration-sized, independently-verifiable, adversarially-reviewed stories on the claim/HEAD/auth seams.

**Alternatives considered.**
- *Replace the bake-off outright (D1-B):* rejected — a mesh regression would take the demo down with no fallback; can't A/B on the dogfooding repo.
- *Blade-run planner (D2-B):* rejected — spends tokens, violates R9's zero-token own-logic rule.
- *Advisory-only `assign` over per-provider claims (D3-B):* rejected — makes the no-same-binary/anti-idle guarantee cosmetic.
- *Continuous coordinator coroutine first (D4-A):* deferred to a follow-up (story #6) — strictly better for *active* background dispatch and always-on dashboard counts, but multiplies the spawn surface; land it after the smaller on-demand loop is green. **Basic reaper liveness is NOT deferred with it** (Architect revision): reap-on-exit (Story #1) + `utilization_watcher` reap (Story #2) cover it without a new coroutine.
- *pane_key→recipient translation map (D5-B):* rejected — needless indirection; the ids are already collapsed to one identity (now scoped per run, which also closes the capacity>1/retry collision).
- *Shared (non-namespaced) DAG across runs:* rejected (Architect revision) — `add_node` REPLACES + `done` accumulates → a 2nd run silently dispatches nothing. Chose per-run `TaskGraph::new(.../<run-id>)` namespacing (Change 2).
- *Compose `decide_phase` into `permission_service::check` (original Story #4):* rejected (Architect revision) — `check` has NO live caller (deferred to v1.1; desktop has no `apohara-safety` dep); composing it would rewrite dead code (Principle-2 violation).
- *Add the phase deny to the `apohara-hooks-server` PreToolUse response (Architect-revision path a):* rejected (Critic revision) — the installed hook DISCARDS the hooks-server response (`curl … >/dev/null 2>&1 || true`); the handler never denies. A phase gate there ships a DEAD gate behind a green test. Chose enforcement on the **live F2.0c CLI claim-guard exit-2 path** (`guard_decision`/`check_claim`, `crates/apohara/src/main.rs`) — the only PreToolUse block Claude Code honors — with `check_with_phase` as an honest pure-seam fallback (path b).

**Why chosen.** D1-A + D4-B is the minimum-blast-radius path that still makes the mesh fully live: one new code branch behind one OFF-by-default flag, one spawn site, reusing every single-writer guard verbatim. It satisfies all three drivers and every principle, and it is the easiest to verify against the bake-off and to kill-switch.

**Consequences.**
- Two dispatch bodies coexist transiently (maintenance cost; bake-off tests kept to prevent bit-rot).
- The claim key changes (node id, not `{provider}-{seq}`) in the mesh body only — concurrency-critical, hence adversarial review on story #1.
- **(Change 2) The TaskGraph/`done` set is namespaced per run** (`<repo>/.apohara/tasks/<run-id>`); **claims stay at the shared `<repo>/.apohara/claims` root** (PID-keyed, read by one `claim_watcher`/`utilization_watcher`). A 2nd run can't be poisoned by a prior run's `done` set; this also dissolves the OQ3 retry id-collision. Cost: per-run subdirs accumulate on disk (GC is a Follow-up — newest-N or age-based prune — not a v1 blocker).
- **(Change 1) Reaper liveness is delivered in #1+#2, not deferred to #6.** The on-demand loop reaps-on-exit; the `utilization_watcher` reaps stale dead-PID claims between runs (≈5 lines, no new spawn surface). A leaked claim is now structurally impossible to strand. Story #6 becomes a true optional enhancement (active background *dispatch*), not the safety net.
- **(Change 3) Phase enforcement moved to the live F2.0c CLI claim-guard exit-2 path** (`guard_decision`/`check_claim` in `crates/apohara/src/main.rs`), NOT the dead `permission_service::check` AND NOT the `apohara-hooks-server` response (which the installed hook discards — a phase gate there would be dead behind a green test). The guard reads the node phase from `APOHARA_PHASE` (source i, v1 first cut, injected by `spawn_blade`) or `<repo>/.apohara/tasks/<run-id>/phases.json` (source ii, flexible follow-up, written by the desktop in the main repo's `.apohara` so a PLAN blade can't rewrite its own phase), classifies the tool → `PureAction`, and `exit(2)` on `decide_phase == Deny`. **NO new Cargo edge** — the `apohara` CLI crate already depends on `apohara-safety` (and `apohara-dispatch`); the Critic-suggested literal `apohara-safety → apohara` edge would CYCLE, so the verified statement is "reuse the existing `apohara → apohara-safety`." Fallback path (b) keeps `check_with_phase` in `apohara-safety` as an honest no-live-caller seam if the CLI-guard extension slips.
- **(Change 4) `MessageSent` audit emission lives in `apohara-mcp`** (the blade's MCP server process), not the desktop — the desktop cannot observe blade-side MCP sends. `ClaimAcquired`/`MergeCompleted` stay desktop-side. New `apohara-audit` edges on desktop (Story #3) and on `apohara-mcp` (if `MessageSent` is pursued).
- **(UI/UX constraint, §6) The wiring must FEED existing signals, not add UI.** The redesign already renders the kanban/graph/active-providers from `DagTask`/`TASKS` (`state/tasks.rs`) + `claim_watcher` (F1.5) + `utilization_watcher` (F2.4). The mesh stories light those surfaces up by writing the SAME signals — claim records keyed by node id (Story #1), real `ready_count` (Story #2). If a mesh story invented a parallel UI state, the redesign would not surface it; "feed the existing signals" is a hard wiring constraint.
- `APOHARA_MESH` graduating to default-ON is a SEPARATE, explicit decision gated on the green dogfooding e2e — out of scope for this plan.

**Follow-ups.**
- F1.6 project-wide NIT: `repo_path.to_str().unwrap()` → `Command::arg(OsStr)` sweep (non-UTF-8 path safety).
- Real `PlanRefiner` impl (spawns a CLI) for consensus mode — currently mock-only; the hook is wired, off by default.
- **(Change 4)** Land `MessageSent` emission in `apohara-mcp::FsMeshBackend::send_message` (add `apohara-audit` to `apohara-mcp`) if it slips Story #3 — it is located there, never on the desktop.
- **(Change 2)** Per-run `<repo>/.apohara/tasks/<run-id>` GC — prune by newest-N (e.g. keep the last 20 run subdirs) or by age (e.g. drop runs older than 7 days) so heavy dogfooding doesn't grow unbounded subdirs. Disk housekeeping, not a v1 blocker.
- **(Change 3)** v1.1 may adopt `check_with_phase` in `permission_service` once it has a live caller (`permission_arbitrator` un-defers it) — the pure seam from path (b) is the seam it consumes.
- Story #6 (continuous coordinator coroutine — active background dispatch) — land after #1–#5 green; NOT required for reaper liveness.
- **(UI/UX, §6)** Real-data wiring is the prerequisite for retiring `data.jsx` fixtures (`buildSwarm`/`buildCandidates`) in the eventual Dioxus port of the redesign; the "Enhance" button → `build_master_plan` and the winning-diff pane → bake-off path are the two cross-mode entry points to honor.
- `APOHARA_MESH` default-ON graduation decision after the dogfooding gate.

## 6. UI/UX Alignment (grounded in the redesign pre-concept)

> Source: `~/Descargas/Apohara-Catalyst-ui-ux/` (`src/data.jsx`, `src/views.jsx`, `src/panes.jsx`). This is a design pre-concept — a React/HTML prototype rendering FIXTURES. The point of this section: **the redesign already assumes the mesh model, and the mesh wiring stories must feed the SAME live signals the desktop already projects, so these surfaces light up with real data instead of fixtures — with no new UI work.** This is a *constraint on the wiring*, not a UI workstream.

### 6.1 The redesign already models BOTH modes (validates D1-A coexistence)

`data.jsx` ships two fixture engines side by side:
- **`buildSwarm(n)`** — N decomposed slices, each carrying `{ id, title, status, runner, dep, stream, gate }` (the mesh "dozens" case). Statuses: `ready / progress / verifying / done / failed`. This is the **mesh** view of work: disjoint slices, each pinned to a runner, with dependency edges.
- **`buildCandidates(phase)`** — exactly 3 providers (`claude-code-cli`, `codex-cli`, `opencode-go`) competing on ONE objective, gates filling per provider, a `winner` emerging near `phase ≥ 0.95` (the **bake-off**).

That the redesign carries **both** engines is independent UI-side confirmation of decision **D1-A** (bake-off ↔ mesh coexist): the surface is already built to render either mode. The mesh stories don't fight the redesign — they fill in its mesh half with real data while the bake-off half keeps its existing live path.

### 6.2 The four surfaces ← the four wiring stories (concrete signal map)

The desktop today renders the kanban from a single `DagTask` UI signal — `state/tasks.rs::TASKS: GlobalSignal<HashMap<String, DagTask>>` (statuses `Pending/Ready/Dispatched/InVerification/Done/Failed/Blocked`, fields `provider_id`, `agent_role`, …) — fed by `claim_watcher` (F1.5), which projects `ClaimStore::list()` → `merged_status()` → `TASKS`. **The mesh stories must feed those same signals; the redesign reads them, not any new state.**

### 6.3 The wiring constraint (load-bearing — feed the signals, don't fork the UI)

The existing redesign surfaces are driven by `DagTask`/`TASKS` (`state/tasks.rs`) + `claim_watcher` (F1.5) + `UTILIZATION` (F2.4). Therefore:
- **Story #1** must write claim records **keyed by the DAG node id** (already its acceptance criterion, for the mesh-identity reason) AND ensure the `DagTask` it upserts carries `provider_id`/`agent_role` so the Board card's runner tag (`#claude-code-cli-0` → `RUNNER_SHORT`) is real — the redesign reads `t.runner`/`provider_id`, so the assignment's provider MUST land on the signal, not just in a log.
- **Story #2** must feed `ready_count` (and keep idle/active honest via the reaper) so the Active Providers rail's `{ready}/N` and `RUN`/`OK`/idle badges reflect reality, not a fixture.
- **No mesh story may invent a parallel UI state.** If a story routed mesh progress through a new signal the redesign doesn't read, the Board/Graph/rail would stay on fixtures. "Feed the existing `DagTask`/`TASKS`/`UTILIZATION` signals" is a hard constraint on the wiring; it is explicitly NOT a request to build new UI in this plan.
- **Status mapping is already defined** by `claim_watcher::merged_status` + `views.jsx::STATUS_TO_DOT`/`COLS` — the mesh path reuses it; it does not introduce a new status vocabulary. (`DagTask` has 7 statuses; the redesign's 5 columns fold `Failed` into Verifying and treat `Pending`/`Blocked` as not-yet-Ready, matching `merged_status`.)

### 6.4 Scope guard

This section adds **no UI deliverable** to the plan. The redesign is a separate (future) Dioxus port; this plan's stories are validated as *sufficient to feed it* once that port lands. The only UI-adjacent obligation folded into the stories is the signal-feeding constraint above (provider on the `DagTask`, node-id claim key, real `ready_count`) — all already implied by Stories #1–#2. Retiring the `data.jsx` fixtures and porting `views.jsx`/`panes.jsx` to Dioxus is tracked as a follow-up, gated on this wiring being green.

## 7. Open Questions (persist to `.omc/plans/open-questions.md`)

- **OQ1 — RESOLVED (provisional):** `MAX_TICKS` defaults to **600** (≈10 min at ~1s/tick, ≥2× the coordinator's 5-min reaper TTL), tunable via `APOHARA_MESH_MAX_TICKS`. The reaper is the normal exit; the bound is the backstop. Remaining sub-question: tune the number once real dogfooding runs reveal typical drain times. Why it matters: too low truncates real work, too high reintroduces hang risk.
- **OQ2 — RESOLVED (Change 4):** `MessageSent` emits in `apohara-mcp::FsMeshBackend::send_message` (the blade's MCP server process), NOT the desktop — the desktop is architecturally blind to blade-side MCP sends. Remaining sub-question: whether the `apohara-audit` dep + sink construction in the MCP server lands in Story #3 or as a fast-follow. Not a location toggle anymore.
- **OQ3 — DISSOLVED (Change 2):** per-run DAG namespacing (`.apohara/tasks/<run-id>`) means a retried node lives under a fresh run-id and cannot collide with a prior attempt's record. The capacity>1 case remains a knob to validate, but the *id-collision* class is closed by per-run scoping. (Kept as a note: with `APOHARA_BLADE_CAPACITY>1` within a single run, two concurrent blades on one node id would still share a recipient — capacity stays 1 in v1.)
- **OQ4 — Consensus refiner reality:** when (if) a real `PlanRefiner` that spawns a CLI lands — it spends tokens, so it needs its own opt-in + budget story. Why it matters: R9 keeps planning zero-token by default; this is the one sanctioned exception.
- **OQ5 — `APOHARA_MESH` default-ON criteria:** what exact dogfooding evidence (how many green runs, on which objectives) graduates the flag? Why it matters: it's the gate between "experimental" and "the product."
