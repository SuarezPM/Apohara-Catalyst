# US-F1.7 — Dogfooding manual gate (F0+F1 mesh)

> **Gate type:** MANUAL. Pablo runs the real desktop against a real repo with
> real heterogeneous CLIs, watches the mesh behave, and **accepts the diff by
> hand**. This runbook is the human-verification half; the automated half is
> `crates/apohara-desktop-dioxus/tests/dogfooding_mesh.rs`
> (`cargo test -p apohara-desktop-dioxus --test dogfooding_mesh`).

## What this gate proves

That the F0+F1 mesh primitives compose end-to-end **with real, opaque,
heterogeneous CLI blades** — the one thing the automated harness deliberately
cannot prove (it simulates blades as in-process tokio tasks). Concretely:
≥2 different real CLIs (claude / codex / opencode) claim distinct work without
double-assignment, exchange poll messages, integrate green through the single
serialized integrator, do not hang, and produce a diff a human judges correct.

## Pre-reqs

1. **Build & launch the desktop:**
   ```
   cargo run -p apohara-desktop-dioxus
   ```
2. **Rust dispatch enabled:** `APOHARA_RUST_DISPATCH=1` (this is the default-on
   path; only unset it to fall back to legacy). Confirm it is set/on for the run.
3. **At least 2 of the active roster on `PATH`:** any two (or all three) of
   `claude`, `codex`, `opencode` must resolve on `PATH` and be logged in via
   their own CLI session (BYOC — no API keys; Apohara wraps the logged-in CLI).
   Verify with `which claude codex opencode`.
4. **A throwaway target:** a **CLONE or feature BRANCH** of a repo you can
   afford to throw away. **NEVER point this at `main`** of anything you care
   about — the mesh writes commits and merges into HEAD.

## Steps

1. **Point at the throwaway repo/branch.** In the desktop, select the cloned
   repo (or checkout the scratch branch first). Re-confirm it is NOT `main` of a
   repo you care about.
2. **Enter an objective.** Type a small, real objective with naturally
   separable work, e.g. *"mejorá X"* where X has ≥2 independent touch-points
   (so the decomposer can hand out ≥2 disjoint tasks).
3. **Watch ≥2 heterogeneous blades claim — WITHOUT double-assignment.** The
   **TaskBoard** must show ≥2 blades of DIFFERENT kinds (e.g. one `claude`, one
   `codex`) each holding a **distinct** task. No task may show two simultaneous
   claimants. (This is the F0.0 cross-process atomic claim doing its job across
   real OS processes — the case the automated harness can only simulate.)
4. **Watch them communicate (poll mailbox).** Blades exchange messages over the
   F1.2 filesystem mailbox (poll delivery). Confirm the mesh-message activity
   surfaces (a blade reacting to / acknowledging another's claim).
5. **Watch integration go green.** The single serialized integrator (F1.6
   `merge`, one HEAD writer, abort-on-conflict) merges each completed branch
   into HEAD. The combined result — **the mesh diff** — appears in the
   **CodeDiffPane**. No conflict residue, no half-merged state.
6. **Confirm NO 120 s hang.** The run must progress and complete without any
   blade stalling out at the ~120 s CLI timeout. (The historical hang was two
   concurrent `claude` children contending on the shared `~/.claude/` session
   lock; the per-binary `runSerialized` FIFO queue + per-blade worktree
   isolation are what prevent it. This gate confirms it holds with real CLIs.)

## Acceptance (what Pablo verifies by hand — the gate)

The gate **PASSES** only when ALL of the following are observed and Pablo
explicitly accepts the diff:

- [ ] **No double-assignment** — TaskBoard shows ≥2 heterogeneous blades on
      DISTINCT tasks; no task ever has two claimants.
- [ ] **Blades communicate** — poll mailbox carried messages between the blades.
- [ ] **Integrate green** — both/all task branches merged into HEAD with no
      conflict; the mesh diff is coherent in CodeDiffPane.
- [ ] **No 120 s hang** — the run completed without a CLI-timeout stall.
- [ ] **Diff ACCEPTED** — Pablo reviews the mesh diff in CodeDiffPane and
      **accepts** it (the human judgment the harness cannot make).

If any box is unchecked, the gate **FAILS** — do not accept the diff; file what
broke (and prefer reproducing it as a deterministic case in the automated
harness if it is a primitive-level regression).

## Automated harness vs. human gate — what each proves

| Property | Automated harness (`dogfooding_mesh.rs`) | Human gate (this runbook) |
|---|---|---|
| No-double-assignment | ✅ proven deterministically — 2 sim-blades contend on the shared `ClaimStore`; the loser gets `AlreadyClaimed`, asserts 2 DISTINCT tasks claimed | ✅ re-proven across REAL separate OS processes / different CLIs |
| Communication | ✅ each sim-blade drains the other's `Mailbox` poll message | ✅ re-confirmed with real blades emitting real mesh messages |
| Integrate-green | ✅ `lifecycle::merge` ×2 → both `Success`; HEAD has both files; `git status` empty; `git fsck` clean | ✅ re-confirmed on a REAL repo with a REAL multi-file mesh diff |
| No-hang | ✅ the round-trip returns fast (no real CLI to contend a lock) — structurally cannot reproduce the real hang | ✅ the ONLY place the real `claude` `~/.claude/`-lock hang can be ruled out |
| **Decomposition into disjoint paths** | ❌ tasks are **manually** pre-decomposed (an opaque blade can't emit the a-priori file manifest the symbol-aware `conflict_matrix` needs — the F1.7 design decision) | ✅ exercises the REAL decomposer turning an objective into separable tasks |
| **Diff is correct & useful** | ❌ asserts files MERGED, not that the work is GOOD | ✅ Pablo's human judgment — the irreducible reason this is a manual gate |

**Bottom line:** the harness locks the mesh *primitives* as a regression-proof,
deterministic unit (claim → graph → mailbox → worktree → serialized merge). The
human gate is what proves the mesh holds with real heterogeneous CLIs **and**
that the integrated diff is something a human accepts — neither of which the
harness can assert.
